# Controlled Optimisation Run #3 - Single NAT Gateway for Dev

## Experiment

Run #3 tested one controlled infrastructure change:

- Run #2: 2 NAT Gateways
- Run #3: 1 NAT Gateway
- Amazon EKS: unchanged at Kubernetes 1.34
- Worker nodes: unchanged at 2 x t3.small
- VPC and subnet architecture: unchanged
- Tagging configuration: unchanged

The purpose was to isolate the cost effect of reducing the non-production
environment from two NAT Gateways to one while documenting the resilience
trade-off.

## Run #2 versus Run #3

Run #2 retained two NAT Gateways.

Run #3 retained the same EKS 1.34 version and worker configuration but reduced
NAT Gateway count from two to one.

| Metric | Run #2 | Run #3 |
|---|---:|---:|
| NAT Gateways | 2 | 1 |
| EKS measured rate | ~$0.10/hour | ~$0.10/hour |
| Core cost per environment-hour | $0.271381 | $0.209652 |

Observed normalised core infrastructure reduction:

approximately **22.75%**.

This whole-stack percentage is an observed normalised result. It is not treated
as the isolated causal saving because the two experiments had different
durations and AWS hourly billing boundaries affect short-lived runs.

## Isolated fixed networking result

The measured AWS unit rates were:

- NAT Gateway: $0.05 per NAT Gateway-hour
- Public IPv4 address: approximately $0.005 per address-hour

Two-NAT architecture fixed rate:

- 2 NAT Gateways = $0.10/hour
- 2 associated public IPv4 addresses = $0.01/hour
- total = $0.11/hour

Single-NAT architecture fixed rate:

- 1 NAT Gateway = $0.05/hour
- 1 associated public IPv4 address = $0.005/hour
- total = $0.055/hour

Reducing the dev architecture from two NAT Gateways to one therefore reduces
the fixed NAT Gateway plus associated public IPv4 rate by:

**50%**

This is the cleaner architectural comparison because the unit count is the
deliberately isolated variable.

## Cross-AZ observation

CUR contained regional data-transfer usage during Run #3:

- InterZone-Out usage amount: 0.255191
- InterZone-In usage amount: 0.267666

The corresponding unblended cost shown in this controlled low-traffic run was
$0.00.

The single-NAT design therefore has an important architectural trade-off:
traffic originating from the other Availability Zone can traverse AZ boundaries
to use the shared NAT Gateway.

At higher traffic volumes this should be evaluated alongside any applicable
cross-AZ data-transfer charges.

The design also removes independent AZ-local outbound egress. For a production
environment, resilience requirements may justify retaining one NAT Gateway per
AZ even when the single-NAT design is cheaper.

## Modelled monthly scenario

Using the measured fixed unit-rate difference:

$0.11/hour - $0.055/hour = $0.055/hour

At 730 operating hours:

$0.055 x 730 = $40.15

**MODELLED monthly fixed-cost reduction: approximately $40.15/month.**

This is a model based on measured unit rates and is not presented as realised
monthly AWS spend.

## Credits

AWS credits materially offset the cash charge during Run #3.

Credits are kept separate from gross Usage cost because credits do not remove
the underlying economic cost of the architecture.

The optimisation comparison therefore uses gross unblended Usage cost.

## Conclusion

Run #3 demonstrated that consolidating the non-production environment from two
NAT Gateways to one reduced the fixed NAT Gateway plus associated public IPv4
rate by 50%.

The observed normalised core infrastructure cost also fell from approximately
$0.271381 to $0.209652 per environment-hour, a reduction of approximately
22.75%.

The experiment also demonstrated the trade-off required in a FinOps decision:
lower fixed cost must be considered alongside reduced AZ-local egress
resilience and potential cross-AZ traffic.

The result is therefore a measured cost optimisation with an explicitly
documented engineering trade-off, rather than a generic recommendation to
remove NAT Gateways.
